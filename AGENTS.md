# FLORUS Agent Guidelines

## Build / Test / Lint

```bash
cargo build --release          # build
cargo test                     # all tests
cargo test <test_name>         # single test (e.g. solver::tests::test_axial_induction_low_ct)
cargo clippy -- -D warnings    # lint — ALWAYS use this, not build output
cargo fmt -- --check           # formatting check
```

### Build quirks

- `.cargo/config.toml` sets `rustflags = ["-A", "warnings"]` — **all warnings suppressed in `cargo build`**. Use `cargo clippy -- -D warnings` for actual lint results.
- `build.rs` copies `default_inputs.yaml` to `OUT_DIR` and optionally runs Python+scipy to convert `src/core/wake/wake_velocity/turbopark_lookup_table.mat` to a Rust lookup table. Falls back gracefully if Python unavailable.

### Comparing with the Python reference

```bash
pwsh -File tools/compare_examples.ps1                # all 65 example pairs
pwsh -File tools/compare_examples.ps1 -Filter layout # a subset
```

The tool runs every Rust example (`cargo build --release --examples`) next to its Python counterpart and writes the two outputs to `output/examples_comparison.txt` (the curated summary of the file is at its end). The Python examples need the virtual environment of the repository (`floris/.venv`, which has numpy and scipy) and the `floris` package of the repository (`PYTHONPATH=<repo>/floris`).

## Architecture

- **Crate type**: Library + binary. `lib.rs` exports the public API; `main.rs` is a thin CLI.
- **Python reference**: `floris/` contains FLORIS v4.6 (Python). **This is the source of truth for behavior.** When adding features or fixing logic, check the Python source first and port accurately.
- **4D array convention**: All spatial fields use `[findex, turbine, y, z]` indexing (`ndarray::Array4`).
- **Wake model dispatch**: `Box<dyn Trait>` via `WakeModelManager`. Implementations in `src/core/wake/{velocity,deflection,turbulence,combination}/`.
- **Turbine types**: Loaded from YAML in `turbine_library/`. Cp/Ct surfaces from `.npz` (Python) or `.csv`.

### Key source layout

```
src/
├── floris_model.rs       # FlorisModel — main user-facing API (mirrors Python FlorisModel)
├── floris_config.rs      # Config parsing from YAML
├── types.rs              # Float = f64, Array1-4 type aliases, NumericDict
├── core/
│   ├── farm.rs           # Farm struct, turbine management
│   ├── flow_field.rs     # Flow field computation
│   ├── solver.rs         # Wake solver loop
│   ├── state.rs          # Mutable state for iterations
│   ├── grid/             # Turbine grid, flow grid
│   ├── turbines/         # Turbine types, Cp/Ct tables, operation models
│   └── wake/             # Wake models (velocity, deflection, turbulence, combination)
├── wind_data/            # TimeSeries, WindRose, WindRoseWRG
├── optimization/         # Yaw, layout, load optimization
├── visualization/        # Cut plane plotting
└── output_formatter.rs   # Output formatting
```

## Code Style

- **Imports**: Absolute crate paths (`crate::core::wake::WakeModelManager`), grouped: std → crates → local.
- **Doc comments**: `///` for public API, `//!` for module-level.
- **Types**: `PascalCase` structs/enums/traits, `snake_case` functions/variables, `SCREAMING_SNAKE_CASE` constants.
- **Float**: Use `Float` alias (= `f64`), not raw `f64`.
- **Arrays**: `Array1`, `Array2`, `Array3`, `Array4` from `types.rs`. Use `ndarray::s![]` for slicing. Clone before mutation to avoid borrow checker issues.
- **Error handling**: Return `crate::Result<T>` (= `anyhow::Result<T>`). Use `anyhow::bail!("...")` for early returns. Avoid `unwrap()` in production code.

## Testing

- Tests go in `#[cfg(test)]` module at end of file.
- Use `approx::assert_relative_eq!` for floating-point comparisons.
- **Regression tests** in `src/core/wake/floris_regression_tests.rs` validate against Python FLORIS values.
- **Consistency test design**: `tests/FLORUS_FLORIS_CONSISTENCY_TEST_DESIGN.md` documents the golden-value cross-validation strategy and test categories.
- **Golden values** live in `tests/golden_values/` (JSON files generated from Python FLORIS).
- Tolerances: 1% relative for power/AEP, 0.5% for Ct, 0.1% for velocity.

## Operation Models

- `set_operation_model(name)` MUST be called **AFTER** `set_layout()` — `set_layout()` recreates the Farm and overwrites the operation model.
- Supported: `"simple"`, `"cosine-loss"`, `"simple-derating"`, `"peak-shaving"`, `"mixed"`, `"awc"`, `"unified-momentum"`, `"controller-dependent"`.
- Power setpoints: Use `POWER_SETPOINT_DEFAULT` (1e12, from `operation_models`) as sentinel for "no limit". **Zero means disabled, not unlimited.**
- `farm.rs` previously carried a bogus `RATED_POWER_DEFAULT = 5000.0` used to seed power setpoints; it was removed in Bug #30 — `set_power_setpoints_to_ref_power` now uses `POWER_SETPOINT_DEFAULT` (1e12), matching Python.

## Wake Model Traits

- `VelocityModel`, `DeflectionModel`, `TurbulenceModel`, `CombinationModel`
- Implement in `src/core/wake/{submodule}/`.
- Use `Box<dyn Trait>` for dynamic dispatch.

## Examples

- Python examples: `floris/examples/`
- Rust examples: `examples/` (mirrors Python naming: `001_opening_floris_computing_power.rs`, etc.)
- Input YAMLs: `examples/inputs/` (gch.yaml, jensen.yaml, turbopark.yaml, etc.)
- **When porting examples from Python**: match the Rust output to Python output numerically. If results differ, fix the Rust implementation — do not use simplified or placeholder implementations.

## Known Limitations

- **Multi-dimensional Cp/Ct tables are supported** (2026-10): the multi-dimensional data file is loaded as a *set of one-dimensional tables keyed by the condition tuple* (`MultiDimConditionTables`, Python `turbine.py:_initialize_multidim_power_thrust_table`), and for every wind condition the nearest specified value of each condition dimension selects the table (Python `turbine.py:_select_multidim_condition`). The operation models are called once per selected table and the results are masked per condition, exactly as Python does. New APIs: `FlorisModel::set_multidim_conditions(...)` (scalar or per-condition values), `flow_field.multidim_conditions` in the input file, and `TimeSeries::multidim_conditions` (the wind-data route overrides the input-file values, as in Python).
- Disabled turbines via `set_operation(disable_turbines=...)` set power to 0; the solver DOES see the (near-zero) setpoint in Ct/AI since the Bug #35 wiring, but disable does not itself trigger wake re-computation (call `run()` after `set_operation` — Python requires the same). Query APIs now refuse stale state: `get_turbine_powers()` errors with Python's "without first running" message after any state-invalidating change.
- `solve_for_points`/`sample_flow_at_points`/`sample_ti_at_points` support the sequential-model family only; `cc` and `empirical_gauss` full-flow solver variants are not ported (sampling errors for those models; `turbopark` is refused exactly like Python).
- *Flow sampling* (2026-10): the points solver referenced the wind shear to the heights of the sampling points instead of the hub height of the farm (`Core::solve_for_points` now passes the farm's hub heights), which scaled the sampled velocities by up to 14 %. `FlorisModel::sample_velocity_deficit_profiles` and `Core::solve_for_velocity_deficit_profiles` implement Python's velocity deficit profiles (the inflow is temporarily made homogeneous by setting the wind shear to zero).
- *IEC turbulence intensity* (2026-10): `TIParams::calculate_ti` used `iref * (15 + offset) / (ws + offset)`, while Python's normal turbulence model is `iref * (0.75 * ws + offset) / ws` (floris/wind_data.py:assign_ti_using_iec_method) — the two agree at 15 m/s but differ everywhere else (the TI at 8 m/s is 8.6 % with the Python formula, not 11.2 %).
- *The flow visualizations follow Python* (2026-10): the cut planes are drawn with the same elements as Python's `visualize_cut_plane` (the axes with their tick labels, the title, the equal aspect of the axes, the filled contour with the levels of matplotlib's `MaxNLocator` and the "coolwarm" colormap), and the turbine rotors and their labels are drawn on top of the flow field (Python's `plot_turbine_rotors` and `plot_turbine_labels`), which were a stub (`TODO`) before. The boundaries of the bands of the filled contour are interpolated over the cells of the grid (Python interpolates them within the triangles of the points) and the figure is rendered at a higher resolution and scaled down, which smooths the edges (matplotlib anti-aliases them). The thin contour lines that Python draws on top of the filled contour are not drawn.
- `get_operation_models()` is a placeholder using hardcoded Ct thresholds, not the operation models' state.
- **Many Rust examples are narrative placeholders or use their own scenarios instead of faithful ports** of the Python examples. Aligned 1:1 so far: `001_opening_floris_computing_power` (values bit-identical), `get_flow_001`/`011`, `006_get_farm_aep` (AEP within 0.03%, wake losses identical), `control_optimization_003`–`008` (SR/Geometric optima bit-identical; AEP within 0.1%), `layout_optimization_004` (gridded layout bit-identical), `layout_optimization_001`/`002` (the SLSQP optimizer reaches the same optimum: 58832.1 MWh against Python's 58824.3 MWh and 13930.0 MWh against Python's 13930.0 MWh), `layout_optimization_003` (genetic random search: the wind resource and the initial AEP match Python's, the final AEP is 58.8 GWh, exactly as in Python), `layout_optimization_005` (separated boundaries: the gridded layout and the random search, 87.6 GWh against Python's 87.6 GWh), `wind_resource_grid_003` (the layout optimization with the wind resource grid: 40.7 / 44.0 / 40.4 GWh against Python's 40.9 / 44.0 / 40.3 GWh), `uncertain_002` (the expected powers are identical to Python's), `heterogeneous_001`–`004` (powers bit-identical to Python; the 2D/3D flow-field statistics agree within 0.02 m/s), `multidim_001`–`003` (powers bit-identical to Python), `floating_002` (powers and farm powers bit-identical to Python), `wind_resource_grid_002` (expected turbine and farm powers bit-identical to Python), `control_types_001/002/004/005` (powers bit-identical to Python), `get_flow_002`–`004` (the sampled velocities, turbulence intensities and velocity deficit profiles are bit-identical to Python), `turbine_001`/`002`/`003` (the library turbine curves, the yaw sweep, the two-turbine-type farm and the runtime turbine definition with a specified power curve are bit-identical to Python), `emgauss_001`/`002` (the four velocity deficit and deflection parameter sets are bit-identical to Python), `floating_003` (the 5 and 15 degree tilt cases are bit-identical to Python), `wind_data_002`/`003` (the IEC turbulence intensity and the value assignment are bit-identical to Python), `004_set`/`005_getting_power`/`007_sweeping_variables` (the wind conditions, the powers and all six variable sweeps are bit-identical to Python), `010_compare_farm_power_with_neighbor` (within 0.5 kW), `003_wind_data_objects` (the time series and wind rose powers are bit-identical to Python). The remaining unaligned examples and their blocking reasons are listed at the end of `output/examples_comparison.txt`.
- **Engine gaps that block the remaining example ports** (not example-only work):
  - *The layout optimizers follow Python* (2026-10): `LayoutOptimizationScipy` now uses the port of scipy's SLSQP solver (`florus::optimization::layout_optimization::slsqp`, a translation of scipy's `optimize/__slsqp.c` and `optimize/__nnls.c`, including the LAPACK routines they use), so it reaches the same optimum as Python (the AEP of the optimized layout of `layout_optimization_001` is 58832.6 MWh against Python's 58824.3 MWh and the AVP gain is 25.2 % against Python's 25.2 %). The random search (`LayoutOptimizationRandomSearch`) is a port of Python's genetic random search (2026-10: the distance-based initialization `_gen_dist_based_init`, the step-distance PMF `_process_dist_pmf`, the per-individual optimization `_single_individual_opt` and the per-generation sorting/selection `_evaluate_opt_step` (including the relegation of the worst individuals); the number of generations, the grid step size of the initialization and the number of relegated individuals are `LayoutOptimizationConfig::n_generations` / `::grid_step_size` / `::relegation_number`). Python's search is time based (it runs until a wall-clock deadline), so the Rust version runs a fixed number of generations and iterations and the final layouts differ; only the deterministic `LayoutOptimizationGridded` was ported exactly. The constraints follow Python: the turbines may lie *on* the boundary (`Boundary::signed_distance`), and the minimum distance defaults to two rotor diameters. The objective is the AEP/AVP weighted with the frequencies and the values of the wind data (`get_expected_farm_power` / `get_expected_farm_value`), normalized with the value of the initial layout (Python's `_obj_func`), and the derivatives are the forward differences with a step of 0.01 in the normalized coordinates (Python's `eps` option; the step of the objective gradient is not flipped at the bounds, while the step of the constraint Jacobian is, exactly as scipy does it). The geometric yaw can be coupled to the layout optimization (`enable_geometric_yaw`, Python's `_get_geoyaw_angles`, which uses the analytic geometric yaw optimizer). `florus::numpy_random::NumpyRandomState` reproduces numpy's legacy `RandomState` (MT19937 with the polar method) exactly, so the random wind resources of the examples are identical to Python's; numpy's newer `Generator` (PCG64 with the ziggurat normal distribution) is reproduced by `florus::numpy_random::NumpyGenerator`.
  - *The WRG parser now reproduces Python's per-turbine roses* (2026-10): the wind roses were already correct; the gap was in the **expected-power queries**, which used uniform frequencies instead of the wind data's frequencies (Python `floris_model.py:get_expected_turbine_powers` uses `wind_data.unpack_freq()`, which is a per-turbine `(n_findex, n_turbines)` table for the wind resource grid). `Core::wind_data_frequencies` now holds the unpacked frequencies and `get_expected_turbine_powers`/`get_expected_farm_power` use them. In addition, `WindRoseWRG`'s flattened data (`wd_flat`, `ws_flat`, `non_zero_freq_mask`) is now built over all (wd, ws) combinations in the C order of the frequency table. `wind_resource_grid_002` matches Python bit-for-bit.
  - *The `ApproxFlorisModel` surrogate is ported* — `florus::uncertain::ApproxFlorisModel` (Python `ApproxFlorisModel`) is an uncertain model with a single wind direction sample point and a configurable resolution of the expanded inputs (`UncertainResolutions`; the wind speed resolution is 0.5 m/s in the example). The example `uncertain_002` is a 1:1 port and the random walk on the wind speed is drawn with `florus::numpy_random::NumpyGenerator` (numpy's `default_rng`), so the realization of the walk and the expected power are identical to Python's (47.68 MW and 47.72 MW). The run times are not comparable.
  - *The uncertainty model covers the wind direction only* — `florus::uncertain::UncertainFlorisModel` implements the wind direction uncertainty (the expansion of the conditions and the Gaussian weighting, Python `uncertain_floris_model.py`), the parallel runner (`run_parallel`) and the `fix_yaw_to_nominal_direction` option (the yaw angles follow the wind direction). The Serial-Refine yaw optimizer accepts an uncertain model through `YawOptimizationSR::optimize_with_evaluator` with an `UncertainPowerEvaluator` (the turbine powers are averaged over the wind direction distribution before they are weighted), so `control_optimization_002` is aligned. The expansion rounds the inputs per column (the yaw angles of every turbine to 1 deg, the power setpoints to 100 W, the AWC amplitudes to 0.1 deg) and the ties are rounded to the even value, exactly as `numpy.round` does.
  - *The wake parameters and the turbine definitions can be changed at runtime* — `FlorisModel::set_wake_config` rebuilds the wake models from a modified configuration (Python rebuilds the model from a modified dictionary) and `TurbineType::build_cosine_loss` + `FlorisModel::set_turbine_type` build a turbine definition at runtime (Python's `build_cosine_loss_turbine_dict`).
  - *The load optimization is ported* — compute_lti, compute_turbine_voc, compute_farm_voc, compute_farm_revenue, compute_net_revenue and optimize_power_setpoints follow Python's load_optimization.py (load_optimization_001 and load_optimization_002 both match bit-for-bit). The get_operation_models query returned a placeholder (the operating regime) instead of the operation model names, compute_net_revenue ignored its A argument and compute_farm_revenue did not apply the values of the wind data; all three are fixed. The derating levels must be set through the model (`FlorisModel::set_operation`), not directly on the farm: writing the farm's unsorted setpoints leaves the sorted setpoints (used by the solver) stale, so the derating has no effect.
  - *The TurbOPark models work with the cubature grid* — the `turbopark` solver accepts a `TurbineCubatureGrid` (Python's `turbopark_cubature.yaml`). At a wind direction where two turbines have the same streamwise position (e.g. 225 degrees in `turbopark_001`), the order of the tied turbines differs from Python's, so the first condition of that sweep differs (the other conditions match to 1e-4).
- *Heterogeneous inflow is wired into the solver* (2026-10): the speed multipliers are interpolated onto the grid points in the **inertial frame** and multiply the sheared initial field, exactly as Python's `initialize_velocity_field` does (`floris/core/flow_field.py`). The application lives in `FlowField::initialize_flow_field_with_coordinates`, so every flow-field initialization (turbine grid, visualization grid, points grid) applies the multipliers — Python's `copy.deepcopy(flow_field)` behaviour. New API: `FlorisModel::set_heterogeneous_inflow_config(HeterogeneousInflowConfig)`; the configuration can also be given in the input file under `flow_field.heterogeneous_inflow_config` (2D and 3D, with `speed_multipliers`, `x`, `y`, optional `z`). Interpolation: `nearest` matches scipy exactly; `linear` uses a Bowyer-Watson Delaunay triangulation with barycentric coordinates (scipy `LinearNDInterpolator`), which can pick a different diagonal than qhull for co-circular points; the 3D case uses trilinear interpolation on structured grids (identical to scipy for affinely varying data, e.g. the FLORIS examples) and falls back to nearest neighbours for scattered locations.
- *Floating tilt in the wake* (2026-10): the tilt angles used by the wake models are the floating tilt interpolated at the local rotor average velocity of the (waked) flow field (Python `farm.calculate_tilt_for_eff_velocities`, solver.py:1305-1311), not the static `tilt_angles_sorted`. `Farm::calculate_tilt_for_eff_velocities` implements it; the empirical Gauss solver uses it, the other solvers still use the static tilt.
- *Wind rose binning* (2026-10): `TimeSeries::to_wind_rose` now uses Python's bin edges (which start half a step below zero), so the bin centers are multiples of the step and the wind directions near 360 are wrapped to negative values (`_wrap_wind_directions_near_360`). The new `TimeSeries::to_wind_rose_with_weights` applies the bin weights (Python `to_WindRose(bin_weights=...)`), and `WindRose::read_csv_long` reads a long-formatted CSV (Python `WindRose.read_csv_long`). The Rust wind rose keeps the full 0–360° / 0–50 m/s bin range, while Python trims the bins to the data range, so the number of conditions differs (the frequencies and therefore the AEP agree).
- *The wake models must not filter the source turbines on their (rotated) x position* (2026-10): the turbine grid is rotated relative to west about the center of the farm, so the most upstream turbines have a **negative** x. The empirical Gauss, TurbOPark, legacy Gauss and cumulative Gauss Curl models skipped every source with `x < 0`, so the upstream turbines did not generate a wake whenever the farm was not centered on the flow direction (e.g. the 5x4 grid of `floating_002` at a cross wind direction). Python has no such filter (the deficit is only masked with the downstream mask `x > x_i + 0.1`), so the filter was removed. `floating_002` now reproduces Python's farm powers **and** its wind-rose AEP (358.861 GWh against Python's 358.861 GWh) exactly, and `emgauss_001`/`emgauss_002`/`floating_003`/`control_types_004` match Python's numbers.
- *The finite differences of the layout optimization follow scipy exactly* (2026-10): scipy computes the gradient of the objective **without** the bounds of the variables (`_slsqp_py.py:361`), so the step of the forward differences is a fixed `+eps` (the perturbed point may lie outside of the unit interval), while the Jacobian of the constraints is computed **with** the bounds and the step is adjusted with the '1-sided' scheme (`_adjust_scheme_to_bounds`). The Rust port flipped the step in both cases, which made the optimizer sensitive to the floating-point details (the debug and the release builds reached different local optima). With the fix, `layout_optimization_002` reaches Python's optimum exactly (13930.0 MWh) in the debug and in the release build.
- *The geometric yaw of the layout optimization uses the yaw bounds of ±30 degrees* (2026-10): Python's layout optimization creates the geometric yaw optimizer with `minimum_yaw_angle=-30.0` and `maximum_yaw_angle=30.0` (`layout_optimization_base.py:92-98`), while the Rust port used the defaults of the yaw optimizer (0 and 25 degrees). The coupled optimization (`enable_geometric_yaw`) now evaluates the same objective as Python (the Rust version reproduces Python's 16515.9 MWh for Python's optimal layout), but it converges to a different local optimum (16126.9 MWh) because the objective is not smooth (the geometric yaw angles jump when the nearest downstream turbine changes).
- *Yaw optimizers were re-implemented to Python parity* (`YawOptimizationSR` = Ny_passes [5,4] two-pass search, `YawOptimizationGeometric` = analytic trapezoid, `YawOptimizationScipy` = per-condition block-coordinate search); `set_yaw_angles` now invalidates the solved state so the solver re-sorts the yaw angles (Python `set()` resets `core.state`).
- `TurbineCubatureGrid`'s `average_method` (`"simple-cubature"`) + `cubature_weights` feed **only** the solver's thrust/axial-induction path (Python `core/solver.py`). `get_turbine_powers()` still averages with the cubic-mean default — Python `_get_turbine_powers` does not forward the grid's averaging to `power()`; do not wire the cubature weights into the power path (verified against Python: gauss_cubature_grid upstream power 1745305.95 W from cubic-mean vs 1735364.46 W from simple-cubature).
- *The layout optimizers use the wind data of the model* (2026-10): the objective is the AEP/AVP of the wind data (`get_expected_farm_power` / `get_expected_farm_value`, i.e. the frequencies and the values of the wind data) — the random search, the boundary grid and the pyoptsparse optimizers used uniform frequencies and a placeholder AVP before. `Core` now keeps the wind data (`Core::wind_data`) and `FlorisModel::set_layout` updates it (Python `floris_model.py:204-207`), so the wind resource grid regenerates the wind roses of the turbines when they are moved; `FlorisModel::set_wind_data` also applies the heterogeneous inflow config of the wind data (a wind rose with a heterogeneous map).
- *The wind rose upsampling follows Python* (2026-10): `WindRose::upsample` makes the wind directions adjacent (`make_wind_directions_adjacent`), interpolates over the padded grid and wraps and sorts the new wind directions. The Rust version wrapped the directions without sorting them, so the wind rose failed the validation and the upsampling silently returned the un-resampled rose (the wind resource grid was therefore not upsampled to a 2 degree wind direction step).
- *The wind resource grid has a heterogeneous wind rose* (2026-10): `WindRoseWRG::get_heterogeneous_wind_rose` (Python's `get_heterogeneous_wind_rose`) builds the wind rose of a reference location together with a heterogeneous map that holds the speed ups of the grid (the ratios of the expected power of the turbine to the expected power at the reference location, as wind speed multipliers).
- *The layout boundaries can be separated regions* (2026-10): `Boundary::MultiPolygon` holds a list of polygons (Python's list of lists of vertices, which becomes a `shapely.MultiPolygon`); a point lies inside the boundary when it is inside one of the regions.
- *numpy's `Generator` is reproduced* (2026-10): `florus::numpy_random::NumpyGenerator` implements numpy's `default_rng` — the PCG64 bit generator (seeded with numpy's `SeedSequence`) with the ziggurat normal distribution (the tables of `numpy/random/src/distributions/ziggurat_constants.h` are in `src/numpy_ziggurat.rs`). The random walk of `uncertain_002` is therefore identical to Python's and the expected powers match exactly (47.68 MW and 47.72 MW). The legacy `np.random.seed`/`np.random.randn` stream is still provided by `florus::numpy_random::NumpyRandomState`.
- *The Python reference can be run* (2026-10): the virtual environment `floris/.venv` has numpy and scipy; the Python examples are run with `PYTHONPATH=<repo>/floris` from the folder of the example (the `floris` package is not installed in the virtual environment, and the `florus` directory of the repository root shadows it when the current directory is the repository root). The build script of the crate does not find the interpreter and always falls back to the runtime calculation of the lookup table.

## Query API semantics (fixed 2026-10, cross-validated in `tests/cross_validation_query_apis.rs`)

- `get_turbine_powers()` routes through the operation model over the SOLVED field with the cubic-mean default (Python `floris_model.py:554-570`), returns layout-order `(n_findex, n_turbines)` in Watts and a `Result` (state check mirrors Python's RuntimeError).
- `get_turbine_thrust_coefficients()` / `get_turbine_ais()` route through `farm.thrust_coefficient` / `farm.axial_induction` with the grid's averaging method + cubature weights, then unsort to layout order (Python `floris_model.py:1017-1057`).
- `turbine_average_velocities()` (Python property parity, `floris_model.py:1798-1804`): rotor average over the solved field with the grid's method/weights, layout order — previously returned a single rotor point in sorted order. `get_turbine_velocities()` remains a layout-order FIRST-POINT sample (no Python equivalent).
- `get_farm_aep(wind_data, hours)` uses the `unpack_freq` contract (Python `get_farm_AEP`): per-condition frequency column `(n_findex, 1)` weights each condition's farm power; a `(n_findex, n_turbines)` table (WindRoseByTurbine) weights each turbine's power. `WindRose::unpack` returns the flattened, zero-freq-filtered frequency aligned with `n_findex`; `TimeSeries::unpack` returns uniform `1/N`.
- `Farm::set_layout` resets the operation arrays (yaw/tilt/setpoints/AWC) when the turbine COUNT changes — previously they kept the old count and `expand_farm_properties` panicked (index out of bounds).
- Floating tilt: `correct_cp_ct_for_tilt` + `floating_tilt_table` are wired into cosine-loss power (interp at the post-density/yaw effective velocity), cosine-loss & controller-dependent thrust (interp at the uncorrected rotor average), and axial induction. Only `cosine-loss` and `controller-dependent` use the interp — matching Python. Test turbine: `nrel_5MW_floating`.
- `sample_flow_at_points` / `sample_ti_at_points` solve the wake ON the points for ALL findices via `Core::solve_for_points` (PointsGrid + `full_flow_sequential_solver`, Python `core.py:230-266`) and return `(n_findex, n_points)`. The solve runs on a scratch flow field; the model state stays intact (Python clobbers `self.flow_field` instead).
